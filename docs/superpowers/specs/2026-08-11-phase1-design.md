## 1. 目标与边界

让这个平台**真的能约人上桌**。0 期交付了账号、好友、账本、借条、排行和一个占位玩法（highcard，比大小），但没有任何真实牌局。1 期补上两款玩法与配套的牌桌界面。

**做**：炸金花、德州扑克、共享的下注轮与彩池模块、牌力评估器、定稿的牌桌界面、两款玩法的规则型 AI（兼作掉线托管）。

**不做**：斗地主、干瞪眼、三公、拖拉机（2/3 期）；锦标赛与盲注递增；真实货币；观战入口（延后，见 §9）。

## 3. 炸金花规则

### 3.1 牌型（从大到小）

| 牌型 | 说明 |
|---|---|
| 豹子 | 三张同点 |
| 顺金 | 同花且连续。AKQ 最大，A23 最小 |
| 金花 | 同花不连续 |
| 顺子 | 连续不同花。AKQ 最大，A23 最小 |
| 对子 | 两张同点，第三张比大小 |
| 单张 | 以上都不是，逐张比大小 |

同牌型比较：先比关键点数，再比次要点数；**完全相同时比花色**（黑 > 红 > 梅 > 方），保证任意两手牌可全序比较、不产生平局。

### 3.2 闷牌

- 开局所有人处于**闷牌**状态（未看牌）。
- 闷牌时的跟注额是明注的**一半**；加注同理。
- 闷牌者可在自己回合**随时看牌**，看牌后转为明牌状态，此后按明注。
- 闷牌者**不能发起比牌**，也**不能被比牌**。

### 3.3 比牌

- 只有**已看牌**的玩家可以发起。
- 向任一在局的已看牌玩家发起，双方私下比较（结果只告知双方"你赢/你输"，不公开牌面）。
- 发起比牌需支付与当前明注**相等**的注额。
- 输者立即出局（视同弃牌），赢者继续。
- **封顶**：房间设定最大轮数（默认 10 轮）。达到封顶后，在局玩家只能比牌或弃牌，不能再加注。

### 3.4 结算

- 只剩一人时该玩家赢下全池。
- 封顶后强制比牌直到剩一人。
- 全员弃牌不可能发生（最后一人自动获胜）。

## 4. 德州扑克规则

### 4.1 流程

发底牌 2 张 → **翻牌前**下注 → 翻牌 3 张 → 下注 → 转牌 1 张 → 下注 → 河牌 1 张 → 下注 → 摊牌。

### 4.2 位置与盲注

- 庄位（D）每局顺时针移动一位。
- 庄位左手第一位下小盲，第二位下大盲。
- **翻牌前**从大盲左手边开始说话；**翻牌后**从庄位左手边开始。
- 两人单挑时：庄位下小盲且翻牌前先说话，翻牌后后说话（标准 heads-up 规则）。

### 4.3 下注

- 无限注：可弃牌 / 过牌 / 跟注 / 加注 / 全下。
- 最小加注额 = 上一次加注的幅度（首次加注的最小幅度为大盲）。
- 全下金额不足最小加注幅度时，**不重新开放**已行动玩家的加注权。

### 4.4 边池

任何玩家全下且其他人继续下注时产生边池。分池算法：

1. 收集所有玩家本局的总投入，按金额升序取不重复值作为分层点。
2. 逐层构建池：该层池金额 = Σ min(每人投入, 该层上限) − 已计入下层的部分。
3. 每个池只由**投入达到该层的玩家**参与争夺。
4. 从最后形成的边池向主池依次结算。

**不变量**：所有池金额之和 = 所有玩家总投入；每个池的参与者数 ≥ 1。

### 4.5 牌力评估（7 选 5）

从 2 张底牌 + 5 张公共牌中取最优 5 张。牌型从大到小：皇家同花顺、同花顺、四条、葫芦、同花、顺子、三条、两对、一对、高牌。

A 可作最大或最小（5-4-3-2-A 为最小顺子）。

**平局分池**：牌力完全相同的玩家平分该池；除不尽的零头按位置顺序（从庄位左手起）分配，保证总额守恒。

## 5. 共享模块

两款玩法共用，也是 2 期斗地主/干瞪眼之外的另一条复用线。

| 模块 | 职责 | 使用者 |
|---|---|---|
| `betting/round.ts` | 下注轮状态机：谁该说话、跟注额、最小加注、何时轮结束 | 炸金花、德州 |
| `betting/pots.ts` | 主池与边池的构建与结算，含平局分池与零头分配 | 德州（炸金花退化为单池） |
| `hands/three.ts` | 三张牌牌型识别与全序比较 | 炸金花 |
| `hands/seven.ts` | 7 选 5 最优牌型与比较 | 德州 |

`hands/*` 是纯函数、无状态，可独立做表驱动测试——这是牌类项目里最该被穷举测试的部分。

## 6. 界面

定稿：方案 A「经典牌室」。参考实现在 `docs/design/table-ui/`，用浏览器打开 `demo.html` 可看完整一手的效果。

### 6.1 必须保留的设计约束

这些不是审美偏好，是踩过的坑：

1. **筹码本体绝不做 2D 旋转**——它是压扁的椭圆，旋转会让它"立起来"。凌乱感靠 `--spin` 转表面条纹。
2. **底池是累积的**——飞过去哪几枚面额，池子就收下哪几枚。按总额重算会让颜色在落地瞬间跳变。
3. **底池只追加 DOM 节点**——层叠靠显式 `z-index` 而非 DOM 顺序。整堆重建会"闪一下"。
4. **筹码落点只依赖自身序号**，不依赖总数，否则每次加钱都挤动已有筹码。
5. **玩家的筹码码成摞，底池是乱堆**——真牌桌就是这样。
6. **音效全部 WebAudio 合成、不加载音频文件**——部署机出站带宽约 4.5 Mbps 且与其他服务共享。
7. **牌面与牌背一律 SVG**，禁止位图（同上）。

### 6.2 布局

9 人桌沿椭圆分布，本人固定在正下方。下注筹码落在座位与桌心之间，本轮结束统一收池。轮到谁行动：头像金边 + 转圈计时器，且只有轮到本人时操作按钮才可点。

### 6.3 首屏预算

首屏 gzip ≤ 300KB 的约束继续有效。玩法代码按需加载：只打炸金花的人不应下载德州的牌力评估器。

## 7. AI

规则型，每款约 1.5 人天。**主要用途是掉线托管与凑人，不是陪练对手。**

- **炸金花**：按牌型强度分档决定跟/加/弃；闷牌阶段按固定轮数后看牌。
- **德州**：按手牌强度 + 位置 + 底池赔率的简单查表；不做对手建模。

托管策略保守：能过牌则过牌，需要跟注时按牌力阈值决定跟或弃。

## 8. 测试策略

沿用 0 期已建立的框架，并补上 0 期缺失的部分：

1. **`fuzzEngine` 必须开启 `probeIllegal`**——0 期这条不变量对真实引擎从未生效。两款玩法上线前各跑 10 万局。
2. **牌力评估器表驱动测试**：`hands/three.ts` 与 `hands/seven.ts` 各覆盖全部牌型、边界（A 两用、同牌型比较、花色决胜）与已知易错组合。
3. **边池不变量测试**：随机生成全下场景，断言「所有池之和 = 总投入」「每池参与者 ≥ 1」「结算后总金币守恒」。
4. **广播路径双连接测试**：断言 B 收到的 `gameView` 不含 A 的底牌——0 期已补，两款新玩法需各自覆盖。
5. **`secretProbe` 需重新设计**：当前实现在终局也检查，而牌类游戏终局普遍摊牌，对真实引擎必然误报。改为「只在对局进行中检查」或由引擎声明终局可公开字段。

## 9. 开工前必须先处理的技术债

来自 0 期最终审查，**在接入真实玩法之前必须修**：

**`Room.act` 的动作校验用 `JSON.stringify` 做结构比较**，要求 `legalActions` 枚举出每一个具体动作实例。比大小只有跟/弃两个动作，够用；但德州的「加注 300」、炸金花的「向老陈比牌」是参数化的，枚举不出来，且键序不同就会导致合法出牌被拒。

必须改为**校验器模式**：引擎提供 `isLegal(state, playerId, action): boolean`，`Room.act` 调用它而非比对枚举结果。

其余延后项（观战入口、`autoRepay` 强制性、重连队列无上限、401 不清 token 等）见 0 期 ledger，按优先级在 1 期内择机处理，不阻塞开工。

## 11. 风险

**边池是德州最容易写错的地方**，且错误直接体现为分错钱。缓解：边池模块独立成纯函数、随机场景不变量测试、结算前后总金币守恒断言（账本层已有）。

**牌力评估器的边界情况**：A 两用、同花顺与顺子的判定顺序、7 选 5 的组合遍历。缓解：表驱动测试穷举 + 与已知牌力排序表交叉验证。

**界面在 9 人满桌时的可读性**：390px 宽屏放 9 个座位 + 公共牌 + 底池 + 操作区。参考实现已验证布局可行，但真机上小尺寸筹码的细节会糊——1a 期间需在真实手机上验证，不能只看桌面浏览器。
