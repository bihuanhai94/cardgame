# 线上纸牌游戏 — 设计文档

日期：2026-08-10
状态：已确认，待生成实现计划

## 1. 项目目标与边界

给朋友之间远程玩牌用的网页平台，非盈利，规模几十人。

支持六款玩法：炸金花、德州扑克、斗地主、干瞪眼、三公、拖拉机。每款都有联网对战和单机（对 AI）两种模式。

**明确不做**：真实货币充值、开放注册、匹配大厅、反外挂风控、运营后台、移动端原生 App。

## 2. 已确认的产品决策

| 决策点 | 结论 |
|---|---|
| 规模 | 熟人小圈子，几十人 |
| 账号 | 需要账号，邀请码注册，昵称+密码，不收手机号/邮箱 |
| 社交 | 需要好友系统，双向确认 |
| 经济 | 金币体系 + 资产排名 |
| 金币模型 | 固定初始资金 + 玩家间零和流转 + 每日小额补给 |
| 借贷 | 玩家间借条（IOU），非"欠系统" |
| 客户端 | 纯网页 PWA，无原生 App |
| AI | 规则型（启发式）AI，兼作掉线托管与凑人 |
| 分期 | 炸金花 → 德州 → 斗地主 → 干瞪眼 → 三公 → 拖拉机 |

## 3. 总体架构

单体服务 + 权威服务端 + 可插拔游戏引擎。

```
浏览器 (React PWA)
   │  WebSocket (对局状态同步) + HTTP (登录/战绩/排行)
   ▼
Node 服务（单进程）
   ├─ 连接层      鉴权、断线重连、心跳
   ├─ 房间管理    创建/加入/座位/开局/托管
   ├─ 引擎注册表  按玩法分发
   │     └─ 游戏引擎 × 6（纯函数，互不依赖）
   ├─ AI 适配器   给引擎喂动作，和真人走同一条路径
   └─ 账务层      复式记账、借条、排名
   ▼
SQLite（用户/账本/借条/战绩） + 房间状态常驻内存
```

### 3.1 三个核心设计决定

**服务端权威 + 视图裁剪。** 所有洗牌、发牌、合法性判定都在服务端完成。发给每个客户端的是**裁剪过的状态**——他人手牌不出现在网络包里。这是防作弊底线。

**引擎是纯函数**：`(状态, 动作) → (新状态, 事件[])`，随机数使用固定种子。带来四项能力：

- 可测试：给定固定牌局断言结果，无需启动服务
- 可回放：只存动作序列即可还原整局，用于战绩、复盘、纠纷仲裁
- AI 免费接入：AI 是另一个动作产生器，走完全相同的通道
- 断线重连：重放动作序列恢复现场

**复式记账账本。** 金币不是用户表的一个数字字段，而是流水表；余额 = 流水求和。一笔交易的所有流水相加必须为 0。启动时校验全局总额，不平立即报警。选择理由：借条系统若用单字段余额实现，必然出现凭空多钱的 bug。

## 4. 游戏引擎抽象与分期

### 4.1 共用底座

- 牌与牌力：牌的表示、种子化洗牌、发牌
- 回合驱动：轮转、超时托管、掉线接管
- 对局骨架：开局 → 动作序列 → 结算 → 写账本 + 写战绩
- 观战/裁剪：一份完整状态 → N 份玩家视图

### 4.2 玩法分类

| 类别 | 成员 | 类内共享 |
|---|---|---|
| 比牌型类 | 炸金花、三公、德州 | 牌力评估器、下注轮、彩池与边池 |
| 出牌接牌类 | 斗地主、干瞪眼、拖拉机 | 牌型识别、压制校验、手牌管理 |

同类玩法一起开发，第二款成本约为第一款的 40%。

### 4.3 分期与工作量

| 期 | 内容 | 净开发量（单人） |
|---|---|---|
| 0 期 | 骨架：账号、好友、房间、账本、借条、WebSocket、PWA 外壳 | ~15 人天 |
| 1 期 | 炸金花 → 德州扑克 | ~10 人天 |
| 2 期 | 斗地主 → 干瞪眼 | ~12 人天 |
| 3 期 | 三公 → 拖拉机 | ~15 人天 |
| AI | 规则型 AI，~1.5 人天/款 | ~9 人天 |

合计约 **60 人天**。按业余投入（每周 10-15 小时）折算全部完成约 5-8 个月；**0 期 + 1 期约 5-6 周即可上线开玩**，之后每 4-6 周解锁一款。

**风险提示**：拖拉机独占约 12 人天，与其他玩法零共享（亮主、扣底、甩牌合法性、级牌升降规则复杂且地方变体多）。排在最后，以便在实际使用后再决定是否投入。

## 5. 账号、好友、房间

**账号**：邀请码注册，昵称 + 密码。邀请关系入库，可追溯。

**好友**：搜昵称/ID 加好友，双向确认。好友关系用于：在线状态、拉进房间、**借条只能在好友之间打**。

**房间**：

- 创建时选玩法 + 参数（底注、人数、局数上限、是否允许 AI 补位）
- 6 位房间号，凭号加入
- 房主权限：踢人、解散、暂停
- 支持观战，观战者同样只收到裁剪后的状态

**掉线处理**：

| 情况 | 处理 |
|---|---|
| 短暂断网（<60 秒） | 座位保留，重连后重放动作序列恢复，其他人看到"网络不稳定"提示 |
| 超时未操作 | AI 托管接管，保守策略（能弃则弃、能过则过），玩家随时收回 |
| 长时间掉线（>5 分钟） | 房主选择「AI 接管至本局结束」或「结算并解散」 |

## 6. 金币、账本与借条

### 6.1 账本

每笔资金变动记为一条流水（账户、金额、原因、关联对局）。一笔交易的流水之和为 0。余额由流水求和得出。启动时校验全局总额守恒。

### 6.2 借条（IOU）

- 仅限好友之间
- **新账号 7 天内不能借出也不能借入**（防小号）
- 借出时：债权人余额 −N、债务人余额 +N，同时生成借条记录（债权人、债务人、本金、状态）
- **不设利息、不设强制期限**——朋友之间收息制造矛盾；期限到期系统也无手段执行
- 还款：可随时手动还，也可开启「赢钱自动优先还款」
- 赖账：系统不介入，但**借条列表对所有好友公开**（谁欠谁、多少、多久）。以社交透明度替代系统惩罚

### 6.3 排名

**必须按净资产排名，不能按余额**：

```
净资产 = 余额 + 应收借条 − 应付借条
```

按余额排会产生刷榜漏洞（向多位好友借款即可瞬间登顶）。按净资产计算，借款动作对排名的影响为 0。

排行榜同时展示三列：净资产、余额、负债。

### 6.4 资金注入

- 新账号固定初始资金（如 10000）
- 每日签到小额补给（如 200，约初始额的 2%）——唯一的外部注入，量小不破坏零和性质，保证输光者次日仍能上小局

### 6.5 结算原子性

一局牌的全部输赢在单个数据库事务内写入，要么全成要么全不成。

### 6.6 战报

每局结束生成可分享的战报（输赢明细 + 关键牌局回放链接）。回放数据本就存在，成本低，是朋友局的主要乐趣来源之一。

## 7. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 生态成熟，PWA 开箱即用 |
| 状态 | Zustand | 牌桌状态不复杂，无需 Redux |
| 样式 | Tailwind | 大量重复小组件，原子类高效 |
| 动画 | GSAP | 发牌/出牌/筹码动画决定"手感"，不可省 |
| 通信 | 原生 WebSocket + 自定义重连 | socket.io 体积（~60KB）在低带宽下不划算 |
| 后端 | Node + TypeScript + Fastify | 与前端共享规则代码 |
| 数据 | SQLite + Drizzle ORM | 类型安全，迁移可控，零运维 |

**规则代码前后端共享**是选型核心收益：牌型判定、压制校验、牌力比较写一份，前端做即时预校验（非法牌立即置灰，无需服务端往返），后端做权威判定。在低带宽 + 百毫秒延迟下，这直接决定操作跟手程度。

### 7.1 客户端硬约束

1. 牌面用 **SVG/CSS 绘制**，禁用位图（整副牌约 50KB 而非数 MB）
2. 首屏包 ≤ **300KB**（gzip 后），玩法代码按需加载
3. Service Worker 缓存全部静态资源，二次打开零网络请求

## 8. 部署方案（现有 119.29.198.188）

### 8.1 现状核实结果

| 项 | 实测值 |
|---|---|
| 系统 | CentOS 7，内核 3.10.0-514，**已 EOL**，uptime 2338 天 |
| glibc | **2.17** —— Node 18+ 官方构建无法运行 |
| CPU / 内存 | 2 核，3.7G（可用 2.9G，已用 552M） |
| 磁盘 | 50G，剩余 38G |
| 公网出站带宽 | **实测 ≈ 4.5 Mbps**（两次测量 4.56 / 4.53，本地生成速度 13.3MB/s 非瓶颈） |
| nginx | 自编译于 `/usr/local/nginx`，含 ssl 模块，**无 http_v2** |
| 现有服务 | `agent-hub`（飞书审批 Bot）、uwsgi console_site、腾讯云监控 |
| 证书 | 仅 `cert/server.crt` 自签，server_name localhost，**无 Let's Encrypt** |

### 8.2 隔离部署（不影响现有服务）

- **运行时**：Node.js 非官方 `linux-x64-glibc-217` 构建，解压至 `/opt/cardgame/node`，不进系统 PATH、不装系统包
- **数据库**：SQLite 单文件，不安装 Postgres
- **进程隔离**：专用用户 `cardgame`、专用目录 `/opt/cardgame`、独立 systemd unit，设置 `MemoryMax=1G` `CPUQuota=80%`，确保最坏情况下只有游戏服务自身被 OOM kill，不波及 agent-hub
- **监听**：`127.0.0.1:3100`，不对外开端口，无需改安全组
- **入口**：`nginx.conf` 的 http 段增加一行 `include cardgame.conf;`，规则全部写在新文件。流程：备份 → `nginx -t` → `nginx -s reload`（优雅重载，agent-hub 零停机）。回滚 = 还原一行 + reload，约 30 秒
- **TLS**：`tyyunan.com` 子域名 + Let's Encrypt **DNS-01** 验证（不占 80 端口、不需停 nginx）

### 8.3 静态资源必须走 CDN

4.5 Mbps 为全机共享。游戏消息本身约 16 kbps/人，几十人仅占带宽 5% 以下，毫无压力；**瓶颈在首屏静态资源**——1-2MB 的包，10 人同时首次打开需 30 秒以上并会打满带宽、拖累 agent-hub。

因此静态资源（HTML/JS/CSS/SVG）必须托管到对象存储 + CDN，VPS 只承载 WebSocket 与 API。此为**硬性要求，非优化项**。

### 8.4 迁移预留

选择 SQLite 的附带收益：迁移到新服务器只需拷贝数据文件与代码目录，成本接近于零。

### 8.5 与本项目无关但需记录的风险

该服务器的系统层风险独立于本项目存在，不计入本方案成本，但应单独处理：

- CentOS 7 已于 2024-06 结束支持，内核停留在 2017 年版本，六年未打补丁
- root 密码曾以明文形式传输，应立即更换并改为密钥登录、禁用密码登录

## 9. 测试策略

引擎为纯函数，因此：

**表驱动规则测试**：每款玩法维护一份「给定手牌 → 期望结果」用例表，覆盖数百组边角规则。牌类游戏的 bug 集中在边角规则（德州边池、斗地主四带二、拖拉机甩牌被毙），而这些恰是手工测试最难覆盖、且**直接涉及金币输赢**的地方。一旦出现"明明赢了却扣钱"，信任即刻崩塌。

**随机对局自测**：每款玩法上线前跑 10 万局随机对局，断言三项不变量：

1. 每局结束后**总金币守恒**
2. **无非法动作被接受**
3. **无死锁**

该测试数秒内跑完，可捕获绝大多数规则实现错误。
